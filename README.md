# context-compactor
把长文本/对话历史里高频重复的短语替换成单 token 符号，从而在发给模型前降低 token 占用
# 节约上下文的思路（kb-skill）

> 目标：搞清 AI 对话里"上下文用量"是什么，市面上省上下文的功能/插件都是怎么实现的，以及一种具体可行的新思路——把高频词/短语映射成单字符来压缩 prompt。

---

## 1. 背景：那个"上下文用量"到底在量什么

- 它不是在量"打了多少字"，而是在量 **token**（模型的最小处理单位）。
  - 中文通常 1 个字 ≈ 1~2 token（GPT 的 cl100k 分词器下常见汉字约 1 token）。
  - 英文约 4 个字符 1 token。
- 每次发一句话，模型收到的是**一整包**：系统提示 + 全部历史对话 + 检索到的文档 + 工具返回结果。
- 关键事实：**像 ChatGPT/Claude 这类对话，每一轮都会把前面所有历史重新发一遍**。所以第 11 轮时第 1~10 轮全在里面，用量条只升不降，撞到模型上限（如 128K）后要么自动丢最早的消息，要么报错。
- 用量百分比 = `本次请求 token 数 ÷ 模型最大窗口`，由 tokenizer（OpenAI 用 tiktoken，各家有各家的分词器）实时数出来。

**结论**："省上下文"的本质 = 在不丢关键信息的前提下，让每次发出去的包裹更小。

---

## 2. 市面上省上下文的方案（分类）

所有方案都能归到两类：

### 2.1 无损路线（原意不变，只是搬了家）
- **滑窗截断**：只保留最近 N 条消息，丢最旧的。最简单，几乎所有聊天 UI 撞上限时的默认行为。缺点：早前的约定/背景会消失。
- **外挂记忆 / RAG**：长文档和全部历史不挤在窗口里，而是存进向量库，每轮只"检索"出相关的几段塞进去。ChatGPT 的"记忆"、各类知识库问答都是这套。
- **语义缓存**：相似问题直接复用之前的回答，连推理都省。适合 FAQ、重复询问。

### 2.2 有损路线（压缩或丢弃，换空间）
- **摘要压缩**：历史快满时，叫小模型把前面的对话"归纳成一段摘要"替换原始多轮（如 LangChain 的 ConversationSummaryMemory）。
- **提示词压缩**：用小模型删掉 prompt 里的冗余词（如微软 **LLMLingua**，号称压到 1/20 仍基本不影响效果）。近无损但仍是"有损"。
- **提炼 / 蒸馏**：从对话里抽关键事实写进长期记忆，而不是把整段聊天塞回去。

**实践组合**：先用滑窗/检索把量控住，逼近上限时再用摘要或压缩救场（无损优先、有损兜底）。

### 2.3 插件是怎么"动手"的（通用流程）
1. **拦截**：浏览器插件注入脚本劫持页面的 fetch/XHR；自己写的应用则在编排层（LangChain / LlamaIndex）拦截。
2. **计量**：用 tokenizer 数当前包裹 token 数，和预算阈值比较。
3. **决策**：没超 → 原样发；超了 → 走压缩/检索分支。
4. **压缩/检索**：调摘要、查向量库、截断历史，把包裹变小。
5. **注入精简上下文 → 发送 API**。

> 伪代码骨架：
> ```python
> msgs = load_history()
> if count_tokens(system + msgs) > BUDGET:
>     old = msgs[:-K]
>     summary = llm_summarize(old)   # 或向量检索 / LLMLingua 压缩
>     msgs = [summary] + msgs[-K:]
> reply = call_api(system, msgs)
> ```

### 2.4 真实例子
- ChatGPT / Claude 自带：系统提示 + 自定义指令 + Memory（只注入关键事实而非全历史）+ 撞上限自动裁剪。
- 浏览器插件：Superpower、ChatGPT Prompt Genius（带 token 计数器）、WebChatGPT（给回答挂网页检索，本质是 RAG）。
- 框架层：LangChain 多种 Memory、LlamaIndex 上下文重组。
- 前沿：MemGPT / Letta（模仿 OS 做"核心/调取/归档"分级记忆）、微软 LLMLingua、tiktoken（计数底层）。

## 3. 一种具体新思路：高频词/短语 → 单字符映射

### 3.1 这是什么
本质是**确定性词典编码 / 语义宏（semantic macros）**——把数据压缩里的"字典法"用到 prompt 上。
做法：统计语料里高频出现的多 token 短语，每个分配一个**单 token 符号**（如 §、¶、⚡），在 system prompt / 长期记忆里**只挂一次**图例（映射表），之后所有发出去的消息都用符号代替原短语。

### 3.2 为什么能省
- "large language model" = 4 token，换成 "§"（1 token），每次出现省 3 token。
- 只要该短语重复出现足够多次，省下的 token 就能盖过图例本身的成本。

### 3.3 4 个硬前提（最容易翻车的地方）
1. **替换符必须是"单 token"**。若 § 本身是多个 token，则白压甚至更亏。必须用 tokenizer 逐字符校验 `n_tokens(symbol) == 1`（很多 emoji 实际是多 token）。
2. **词典成本要摊销**。图例本身占 token，所以只在"术语高频重复"时划算；短聊天、一次性问答别用。
3. **别浪费槽位在子串上**。若同时把 "large language model" 和它的子串 "large language" 都选进字典，子串永不被用到，白占槽位。应做**非重叠贪心选择**：长短语已覆盖的子串直接跳过。
4. **模型要能可靠解压 + 单字符语义弱**。单个生僻字符语义信号很弱，模型可能"想不清楚"或解错。工程经验：
   - **只压历史/长文，不压当前提问**：让模型在完整文本上推理新问题，过去轮次才存压缩版。
   - 词典在整段会话中保持一致，不要中途改。

### 3.4 部署形态
- **只压输入**（最常见）：你压缩 outgoing，模型读压缩版、照常输出原文。简单，但输出不省。
- **输入输出都压**（LLMLingua 思路的确定性版）：让模型也用符号回复，你这边再解压。省得最多，但要约束模型别自创符号。

### 3.5 实测（用 tiktoken cl100k_base 真实计数）
- 原始：**696 tokens**
- 压缩后正文：**558**
- 词典（图例，只发一次）：**39**
- 合计：**611**，省 **85 tokens ≈ 12.2%**
- **盈亏平衡点：0.28 轮**（同一批术语重复出现几乎立刻回本）

> 12% 是轻量语料的保守值；真实长文档/长对话里满是行话时，压到 30%~50% 很常见。压缩率上限取决于"文本中有多少比例由重复短语构成"。

### 3.6 适用 vs 不适用
- **适用**：长文档、多轮长对话、术语/专有名词/代码标识符高频重复的场景。
- **不适用**：短聊天、低频重复、创意生成类任务（压缩会伤表达）。

### 3.7 与其他方案的关系
它是把"有损/无损"里**摘要压缩**的"软"做法，换成了**确定性、可逆**的做法——不靠小模型归纳，而是固定映射表。优点：可预测、零额外推理成本、能精确还原。缺点：压不掉"低频但占地方"的内容，那种还得靠摘要/RAG 兜底。实战里常和滑窗、RAG 组合：高频术语走符号映射，长文档走检索。

## 4. 算法步骤（实现要点）

1. 对语料（或当前会话累计）做分词，统计 1~3 元短语频率。
2. 候选 = 短语 token 数 ≥ 2 且出现次数 ≥ 2 的条目；潜在收益 = `次数 × (原短语token数 − 1)`。
3. 按收益降序，**非重叠贪心**选取：跳过已被选中长短语覆盖的子串；单条收益需盖过其图例成本才入选。
4. 从候选符号池里挑出"经 tokenizer 校验为 1 token"的符号逐个分配。
5. 拼出图例（只发一次），对正文做最长优先替换（避免嵌套替换）。
6. 计量：比较 `原token数` 与 `图例 + 压缩正文` 的 token 数，输出压缩率与回本轮数。

> 可直接运行的 demo：`context_compactor_demo.py`（含单 token 符号校验 + 非重叠贪心选择）。把 SAMPLE 换成自己的长文本即可测压缩率。

## 5. 风险与边界（小结）
- 模型解压可能出错 → 关键场景保留原文或做解压校验。
- 单字符语义弱 → 不要压当前问题，只压历史。
- 词典一致性 → 中途改映射会让模型混乱。
- 低频文本无收益 → 先判断重复密度再决定是否启用。
- 与摘要/RAG 互补，不要指望单一手段解决所有上下文膨胀。

## 6. 已落成可复用 Skill（context-compactor）

本思路已封装为 WorkBuddy 用户级 Skill，可手动触发，开箱即用。

- **位置**：`~/.workbuddy/skills/context-compactor/`（含 `SKILL.md` + `scripts/compact.py`），并已打包为 `context-compactor.zip`。
- **触发**：对助手说"压缩上下文 / 省 token / 把这段对话压缩一下"；或自行运行：
  ```bash
  python scripts/compact.py --input long.txt --output packed.txt --stats
  ```
- **能力**：支持中英文混合；自动用 tokenizer 校验替换符为单 token；非重叠贪心选词（长短语已覆盖的子串不占槽位）；输出"映射表 + 压缩正文"，并报告压缩率与回本轮数。
- **实测（中文样本）**：183 → 157 token，**省 14.2%**，盈亏平衡 **0.46 轮**。4 个高频中文短语（大型语言模型 / 上下文窗口 / 训练数据 / 神经网络）映射为 §¶●★；英文因样本中出现次数少（2 次）未达词典成本阈值，被正确跳过。
- **落地时修正的两个坑**（已固化进脚本）：
  1. CJK 按"每条 run 单独计数"时 `dict.update` 是覆盖而非累加 → 改用 `Counter` 累加，否则跨句重复短语计数被清零、全被过滤。
  2. 中文词串默认最长只取 4 字，会把 6 字整词切碎 → 提到 6 字，并做非重叠筛选。
- **性质**：本 Skill 为**手动触发**（对应方案 A）。若要"每轮自动压"，需改为请求拦截层（方案 B）——在 API 调用前自动计量+压缩、收后自动解压。

### 6.1 方案 B：请求拦截层（已实现，`auto_compactor.py`）
- 把压缩做成**透明中间件**：`AutoCompactSession` 包住任意"发送 messages → 返回回复"的传输函数（默认 `DryRunTransport` 可离线演示，也可传 `openai_client.chat.completions.create`）。
- 每轮 `chat()` 自动：用全量历史重建字典 → 压缩除"最近 N 条用户消息"外的所有历史 → 把图例拼进 system 消息（只发一次）→ 调传输 → 存原文。对调用方无感。
- **演示实测（6 轮，中文）**：字典 8 条；原文历史 612tok → 实际发送 352tok，**累计省 42.5%**。前几轮字典未摊薄为负属正常，第 3 轮起转正并随历史增长（自动、越滚越省）。
- 关键参数：`keep_raw`（最近几条用户消息保持原文，让模型在完整文本上推理新问题）、`cjk_max`（中文最大词长，默认 12 以捕获整段重复短语）、`top`（字典条数上限）。
- 已知限制：CJK 贪心选词在"整句重复"时仍可能产生少量相邻滑动窗碎片（已用 4 字重叠守卫缓解）；真实场景重复多为术语，字典干净。双端压缩（模型输出也压成符号、本地解压）可作为后续增强。

### 6.2 方案 B 现在可加载 Skill A 产出的固定词典（手动建词库 + 自动套用）

此前 B 是"每轮从全量历史重建字典"，没有接入外部预置字典的口子。现已补齐 `load_dictionary(path)`：

- `AutoCompactSession(predefined_dict="dict.txt")` 或 `sess.load_dictionary("dict.txt")`：直接加载 Skill A 产出的映射表，此后**字典固定不变**，跨轮完全一致。
- 支持两种文件格式：
  1. 图例文本：Skill A 输出的 `{符号} = {短语}` 一行一条（`Dictionary ...` 头、空行自动忽略）。
  2. `.json`：自动识别 `{短语: 符号}` 或 `{符号: 短语}` 两种方向。
- `allow_grow=True`：以预置词典为种子，每轮再自动发现并追加少量新高频词（受 `top` 约束）。

**正确组合不是把 A、B 串联**（双重压缩会冲突），而是 **A 建库、B 套用**：A 针对某领域语料生成一份固定映射表，B 接入时直接加载、不再每轮重建。这对稳定术语库（项目专有名词、行话）最省、最稳。

**实测（4 轮中文，仅 4 条预置词条）**：
- 固定字典模式：字典恒为 4 条预置词条，跨轮不漂移，累计省 ~16%。
- 补词模式（allow_grow）：在 4 条基础上自动追加 4 条，累计省 ~28%。
- 对比默认"每轮重建"：在逐字重复文本上会选出长片段（重复性文本的固有特性），而固定词典模式反而给出更干净、稳定的词典——正是"稳定术语库"想要的形态。

注意：固定词典模式效果取决于预置词典的覆盖度；预置越全、术语重复越多，节省越高。Skill A 的 `compact.py` 可在大语料上一次性产出高质量词典供 B 长期复用。
